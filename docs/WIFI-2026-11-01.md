# Songyuan Wi-Fi：实现说明（2026-11-01）

适用范围：Redmi K100 Pro Max / songyuan / SM8850，data-a-live 裸机链，iOS 16.7.16 用户态。
本文只写本机已经量到的事实、公开上游能核对的事实，以及还没量到所以不能当常数用的项。
触摸已经在这条链上走通（见 `ANALYSIS-2026-11-01-touch.md` §9–§10）。Wi-Fi 还没开始做对的那一层。

## 0. 结论

这颗芯片是 **WCN786x / peach**，PCI **`17cb:110e`**。Android 上把它跑起来的驱动是 **`cnss2` + `qca_cld3_peach_v2`**，接口名 `wlan0`。

现在内核里的 `fuxi_wlan.c`（补丁 `0099`，boot-arg `fuxiwlan`）是 **另一颗芯片、另一颗 SoC**：

- 设备号写死 `17cb:1107`（WCN7850）
- DBI / iATU / 配置窗写死 `0x60000000` / `0x60100000` / `0x60400000`（fuxi / SM8550 的窗）
- 它做到 MHI/BHI 寄存器只读转储就停，**不创建 `en0`，也不回答 Apple80211**

所以 `fuxiwlan=1` 不能在 songyuan 上打开。PARF `0x1c00000` 和 PHY `0x1c06000` 碰巧与 0099 相同，只说明根复合体的前两个寄存器块地址一样，不说明后面的窗、固件和设备号一样。

iOS 能上网需要两段，缺一不可：

1. **无线侧**：按本机设备树把 PCIe RC0 点亮，链路上出现 `17cb:110e`，用**这台手机自己的** peach 固件走 MHI + QMI，进入 mission mode。
2. **iOS 侧**：造一个 `en0`，用 Apple80211 ioctl 回答 `wifid` / 设置。这段与芯片无关，hackios 的 `redwood_net.c` + `redwood_apple80211.c` + `RedwoodWLAN.cpp` 是现成形状。redwood 的射频加载（WCN6750，片内 DSP，没有 PCIe）不能搬。

主线 `ath12k` 和 `linux-firmware` 的 `ath12k/` 目录目前只有 WCN7850（`1107`）、QCN9274、IPQ5424、QCC2072。没有 `17cb:110e`，也没有 `ath12k/PEACH`。把 WCN7850 的 `amss.bin` / `board-2.bin` 拷过来不会被这颗芯片接受。

## 1. 本机实测（可以当事实用）

来源：`docs/android-groundtruth-subsystems.txt`、`docs/REUSE-MATRIX.md` 的 live DT 表、`ANALYSIS-2026-11-01-touch.md` §12–§13（已用 `/soc/pcie@1c00000` 复核过一轮错误）。

### 1.1 枚举

| 项 | 值 |
|---|---|
| 根复合体 | `0000:00:00.0`，`17cb:0123` |
| 无线端点 | `0000:01:00.0`，**`17cb:110e`** |
| Android 接口 | `wlan0`，另有 `p2p0` `p2p1` `wifi-aware0` |
| 平台模块 | `cnss2` `cnss_nl` `cnss_plat_ipc_qmi_svc` `cnss_prealloc` `cnss_utils` `wlan_firmware_service` `spi_cnss_proto` |
| 无线驱动 | **`qca_cld3_peach_v2`** |
| 设备树 | `/soc/wcn786x`（`qcom,wcn786x`），`/soc/pcie@1c00000/pcie_rp/cnss_pci0`，`qcom,cnss-peach`，`supported-ids = <0x110e>`，`qcom,wlan-rc-num = <0>` |

`wlan-rc-num = 0` 表示挂在 **PCIe RC0**，也就是 `pcie@1c00000`。不要去找 PCIe1/PCIe2。

### 1.2 RC0 寄存器（live DT `reg` / `reg-names`）

| 名字 | 物理地址 | 长度 |
|---|---|---|
| parf | `0x1c00000` | `0x3000` |
| phy | `0x1c06000` | `0x2000` |
| dm_core（DBI） | `0x400000000` | `0x10000000` |
| elbi | `0x400000f20` | `0xa8` |
| iatu | **`0x410000000`** | `0x1000` |
| pcie_sm | `0x1d07000` | `0x7000` |

iATU 是独立区域。不要用 DBI+`0x1200`，也不要使用 0099 里的 `0x60000000`。

`ranges` 是 3 组、每组 7 个 cell，2026-11-02 从 `/proc/device-tree/soc/pcie@1c00000/ranges` 读出：

| 类型 | CPU / PCI 地址 | 长度 |
|---|---|---|
| `0x01000000` | `0x40200000` | `0x100000` |
| `0x02000000` | `0x40300000` | `0x3d00000` |
| `0x43000000` | `0x4_10100000` | `0x2_eff00000` |

Android 把 BAR2 放在 `0x40300000`（32 KiB）、BAR0 放在 `0x40400000`（2 MiB），都落在第二组里。出站 MEM 窗口用这一组，不要用 `0x60400000`。

配套节点：`crm@1d01000`（`qcom,pcie-crm-v3`），`pdc` 用设备树里的 canoe PDC，`interconnect@16c0000`（`qcom,canoe-pcie_anoc`）。

中断号 140、149、150、151、152 是 **RC 节点**上的，名字还没对上。M1/M2 用轮询。不要把 140 当成端点 MSI。
`qcom,target-link-speed = 3`。`qcom,aux-clk-freq = 0x14`，这是设备树里的原值，不要换算成 MHz。复位名：`pcie_0_core_reset`、`pcie_0_phy_reset`。电源域名：`gdsc-phy-vdd`。
live DT 还有 `qcom,phy-sequence`（2388 字节）。上游 `pcie-qcom.c` 这份表里没有同名属性。本机 PCIe 驱动若在 init 里读它，它就属于第一次点亮；驱动不读，就不要把它当成失败后补写的一串数。

### 1.3 引脚

| 功能 | GPIO | 极性 / 备注 |
|---|---|---|
| PERST | TLMM 102 | flags `0`，高有效 |
| WAKE | TLMM 104 | |
| CLKREQ | TLMM 103 | `qcom,pcie-clkreq-offset = 0x2c48` |
| WLAN_EN | TLMM 16 | `wlan-en-gpio`，与 `wcn786x` 的 `wl-reset-gpio` 是同一脚 |
| SW_CTRL | TLMM 18 | 与 BT 的 sw-ctrl 共用，先别改成输出去抢 |
| WLAN_SW_CTRL | TLMM 19 | |

本机设备树里**没有** `pci-pwrctrl-pwrseq` 节点。主线内核那套 pwrseq 匹配不要搬。

### 1.4 SMMU

`iommu-map` 的实测值是 `<0x0 0x6b 0x1400 0x1>, <0x100 0x6b 0x1401 0x1>`：

- RID `0x0` → phandle `0x6b`（apps SMMU），stream **`0x1400`**
- RID `0x100` → 同一 phandle，stream **`0x1401`**

`0x6b` 是 phandle，不是 stream id。第四格是 RID 长度 `1`，不是 SID 掩码。2026-09 上游把步长改成 `3 + #iommu-cells`（五格）。这份手机上的 `pci-msm-drv.ko` 不是那一版：`msm_pcie_get_iommu_map` 被内联在 `msm_pcie_probe` 里，条目数是属性字节长度右移 4，也就是 **16 字节、四格**。它取第 0 格当 BDF、第 2 格（偏移 8）当 SID，phandle 和长度不写进表。`qcom,smmu-sid-base` 读进设备对象偏移 `0x5f4`，live 值是 `0x1400`。SID 减去这个基址后只留一个字节。端点 requester `0x100` 的 SID 是 `0x1401`，减完是 `1`。

`msm_pcie_config_sid` 把表放在 **PARF+`0x2000`**（`add` 的立即数是 `2 << 12`），先把 PARF+`0x2c00` 的 bit 0 清掉，再对这张表 `memset_io` `0x400` 字节。哈希是 `crc8_populate_msb(table, 7)`，输入是 BDF 的大端两字节。表项是 `(bdf << 16) | ((sid - base) << 8)`，下标是这个 CRC。对 requester `0x100`：CRC 是 `0x15`，表项 `0x01000100`，写到 PARF+`0x2054`。槽已被占用时哈希加 1 再试。五格步长会把这条 SID 读成 phandle，表是空的，DMA 标成 SID 0。
`cnss-peach` 的 `reg` 是 `0xb0000000`、长度 `0x10000`，名字是 `smmu_iova_ipa`，这是 IOVA 窗，不是 MMIO。`msi-map` 也在这棵树里，数值还没写进本文；M4 之前从 live DT 抄下来，不要用下面的 RC 中断号代替。

### 1.5 供电

songyuan 这颗 `cnss-peach` 在 live DT 里绑了 **七路**，名字以本机为准：

`vdd-wlan-ant-share`、`aon`、`cx`、`dig`、`io12`、`rfa1`、`rfa2`

公开的 `sun-peach-cnss.dtsi` 是另一组七路（有 `vdd-wlan-io`，没有 `cx`）。WCN7850 的 kiwi 节点是八路。电压和负载只认本机每个 rail 的 `qcom,vdd-wlan-*-config`。`cnss2` 的 `power.c` 用 `devm_regulator_get_optional()`，缺哪路由设备树决定，没有一份“必须七路全开”的通用表。

冷启动校准由 `qcom,wlan-cbc-enabled` 打开。cnss2 在文件系统就绪后投递 `CNSS_DRIVER_EVENT_COLD_BOOT_CAL_START`，并在校准完成前不注册 `qca_cld3`。驱动注释里的 “CBC is the 1st step” 指无线驱动初始化，不是 GPIO 上电。点亮 PCIe 不依赖它。校准会再走一遍上下电，上电函数要能重入。
同一节点还有 `rf_clk`。`cnss_power_on_device()` 先开主电源和时钟，再把 `wlan_en` 选到 active，然后 `udelay(1000)`。这个 1000 是微秒。每路电压和负载用 `qcom,vdd-wlan-*-config`。sheng 上 “没写 RPMh 模式则 rail 实际关着” 是那块板的记录，不是这份 `power.c` 的步骤。`spi_cnss_proto` 在模块列表里不表示无线走 SPI。

### 1.6 蓝牙不是这条 PCIe

BT 在同一颗 WCN786x 上，但是 **UART HCI**：`hsuart0` → QUP3 `qup_uart@1994000`，Android 设备节点 `ttyHS0`，模块 `hci_uart` / `btqca` / `btpower` / `mi_ubt`。Wi-Fi 的 MHI 下载不要顺手去初始化 BT。

## 3. 公开项目里，什么能搬、什么是别的芯片

| 项目 | 芯片 | 和我们的关系 |
|---|---|---|
| 本机 Android `qca_cld3_peach_v2` + `cnss2` | **就是 `17cb:110e`** | 唯一已证明能让这颗芯片出 `wlan0` 的软件。顺序和 QMI 以它的反汇编为准 |
| data-a-live `0099` / `fuxi_wlan.c` | WCN7850 `17cb:1107`，窗在 `0x60000000` | 只借“分步 boot-arg、做完一步再做下一步”的方法。地址表和 BHI 镜像不能用 |
| hackios `redwood_wifi.c` | WCN6750，片内 WPSS，无 PCIe | 射频加载整条不能用 |
| hackios `redwood_net.c`、`redwood_apple80211.c`、`RedwoodWLAN.cpp` | 与芯片无关 | **iOS `en0` / wifid 这一层要照这个形状做** |
| hackios K90 `mhi_pcie.c`（annibale / SM8750） | WCN7850 `1107`，节点 `qcom,cnss-kiwi` | 分步只读的方法可参考。它的入站窗是 `0x40300000`，不是本机 DBI。GPIO 16/18/19/102/103/104 和本机撞号，不表示芯片相同 |
| hackios lemonade `WIFI-QCA6490-PLAN.md` | QCA6490 `17cb:1103` | 已经在 iOS 里走通扫描、关联和 DHCP。MHI 的坑见 §3.1。寄存器和固件不能搬 |

| 主线 `ath12k` | 设备表里是 `1107` 和 `1109` | 数据面结构（CE/WMI/mac80211）是长期目标。今天没有 `110e`，不能当现成驱动编译进来 |

没有找到一份已经合进主线、并且绑定 `17cb:110e` 的 ath12k。UniXNU 的 `devices.toml` 目前只有 sheng。hackios 公开树里的无线是 redwood（6750）、lemonade（1103）、K90（1107）。社区 peach 补丁（窗口寄存器、QDSS、冷校准）各树不一致。

### 3.1 这些项目里值得留下的坑

形状是对的，常数不是。sheng 的 `sheng-wifi` 和 K90 的 `pcie=N` 都是：先只读，链路起来再读配置空间，BAR0 的 MHI 寄存器读完再下载。lemonade 用同一条边界把 `amss.bin` 送进 BHI，再经 BHIe 送完整镜像，然后才做 QMI。

照搬会坏的地方：

1. **链路没起来就读端点配置空间，总线会挂。** K90 把 DBI 读放进第一步时，开机约 8 秒后 USB 不再应答。端点配置空间必须等 LTSSM 到 L0 之后。
2. **sheng 的电气电平不能抄。** 它的 PERST 是低有效：先拉低，WLAN_EN 先低 150 ms 再拉高，RC 时钟和 PARF 配好后至少再等 100 ms，然后 PERST 拉高，再开 LTSSM。本机设备树 flags 是 0（高有效），复位电平按本机标志，不按 sheng 的引脚高低。
3. **只建 SMMU context 不够。** sheng 和 lemonade 都还要写 PARF 的 BDF→SID 表（CRC8，requester `0x100`）。不写这张表，设备 DMA 的 stream 对不上，SBL 取镜像会失败。这张表和 SMMU 一样，放在只读 dump 之后、下载之前。
4. **`MHIVER = 0xdeadbeef` 不是成功。** lemonade 在 PBL 里见过这个值。成功只看 BHI/BHIe 状态和执行环境。
5. **固件版本差一个构建就会卡死。** sheng 上 c7-00108 能跑，c2-00259 卡在按需分页。cnss2 按芯片 major 在 `amss.bin` 和 `amss20.bin` 之间选。用手机自己那一份，不要用 sheng 或 linux-firmware 的相邻包。
6. **XNU 页是 16 KiB，SMMU granule 是 4 KiB。** sheng 的 DMA 从已经为该 stream 建好的 IOVA 区里切，地址是设备看到的 IOVA，不是 CPU 物理地址。缓存要在设备读之前清干净。
7. **不要进 Ath12kWifi 的 stage 5。** 那个组件的硬件表是 1107 / 1109 / QCC2072。sheng 自己在 `0x110717cb` 不对时直接返回。我们读到的如果不是 `17cb:110e`，同样停。

## 4. 进 iOS 的链路（我们这条，不是 Android 的 wlan0）

iOS 16.7.16（这套用户态是 iPhone X）认无线的方式：

```
设置 / wifid
    │  Apple80211 ioctl（没有 user client 时走 SIOCGIF80211 / SIOCSA80211）
    ▼
en0（KPI 以太网接口）
    │  不认识的无线 ioctl 交给 apple80211 层
    ▼
一个只带属性的 IO80211Controller
    │  让 configd 给 en0 建网络服务
    ▼
真正收发的射频驱动（现在还没有）
```

hackios 已经把前三层做成芯片无关的三件套（`wcn7850-plan.md` §1.2）：

- `redwood_net.c`：`en0`。发送方在 `transmit()` 返回后会放掉 mbuf，驱动必须自己拷贝，直到 DMA 完成。
- `redwood_apple80211.c`：回答 wifid 的 ioctl，用 kern_event class 6 / subclass 1 报扫描和连接。
- `RedwoodWLAN.cpp`：注册表里的假 `IO80211Controller`，不碰硬件。

射频驱动只通过一个很窄的边界把扫描结果、连接状态、收发缓冲交给这三层。边界稳定之后，换芯片不用改 wifid。

我们内核里**还没有**这三层。`0099` 停在 “读 MHI 寄存器并打印”。因此即使将来 PCIe 链路正确，iOS 设置里也不会出现 Wi-Fi，直到 `en0` 和 Apple80211 接上。

和已经跑通的子系统的关系：

- 触摸：SPI，与 PCIe 无关。不要为了 Wi-Fi 改 QUP4。
- ADSP / 扬声器：GLINK 走 `adsp_apps`。Wi-Fi 的 QMI 走无线端点自己的 MHI 通道，不走 ADSP。
- 显示 / GPU：已占用自己的 SMMU 流。Wi-Fi 用 stream `0x1400` / `0x1401`，建表时不要覆盖 GPU 的 context。

## 5. 常数

窗口寄存器和 `pcie-sm-debug` 仍不能写成判断条件。BDF→SID 和 BHI 分段长度已经从本机 ko 里读出。

1. **PCIe 窗口寄存器不在 M1，也不在 MHI 寄存器 dump 上。** 上游 ath12k 把已有芯片的窗口宏写成 `0x310c`，`0x3278` 只在 QCC2072 的 probe 里替换它。那份“已有芯片”名单是 `1107` 和 `1109`，没有 `110e`，所以 `0x310c` 不是 peach 的已确认值。cnss2 对小于 `0x80000` 的偏移直接读 `BAR + offset`。`MHIREGLEN`、`BHIOFF` 都在这段里。需要窗口的是后面的 CE。到那一步，先从本机 `cnss2.ko` / `qca_cld3_peach_v2.ko` 里找 remap 偏移。ko 里还没有这个数时，试探顺序只允许先读 `0x310c`，读回全 1 再读 `0x3278`。全 1 的那个偏移就是错的。M1 两个都不碰。
2. **`qcom,pcie-sm-debug` 的一组偏移只记录，不解释。** 不能用它们判断链路。上游 `pcie-qcom.c` 源码里有 `#define PARF_LTSSM 0x1b0`，bit 8 是使能，`[5:0]` 是状态。这是 sm8550 那档 IP 的布局。canoe 不在上游 compatible 表里，所以 M1 可以把 `PARF+0x1b0` 的读数写进日志，这个读数不进入 `if`。通过条件只有配置空间里的 `17cb:110e`。DBI `+0x80` bit 29 只在 K90 那份 `pci-msm.c` 里对过，这里不用。
3. **BDF→SID 按本机 `pci-msm-drv.ko` 写。** 表在 PARF `0x2000`，旁路位是 `0x2c00` 的 bit 0，步长是四格。端点这一条写 PARF+`0x2054` = `0x01000100`。只读 dump 不写这张表。细节在 §1.4。
4. **BHI 要等终态，分段长度已经量过。** `BHI_STATUS` 的 `[31:30]`：2 成功，3 错误，0 复位。0 表示还没完，不是失败。门铃之后轮询到 2 或 3，或者超时。`MHIVER = 0xdeadbeef` 不在头文件里，不能当判据。`cnss_pci_register_mhi` 里，设备号等于 `0x1102` 时 `sbl_size` 是 `0x40000`，其他设备号是 `0x80000`；`seg_len` 固定 `0x80000`。peach 是 `0x110e`，所以 **`sbl_size` 和 `seg_len` 都是 512 KiB**。这两个字段在 `mhi_controller` 的 `+0x80` 和 `+0x88`，`mhi_fw_load_handler` 按 `!sbl_size || !seg_len` 的顺序检查。镜像用这次启动已经加载的 `peach/amss20.bin`。

## 6. 实现顺序

每一步一个变量，退出条件写在日志里。没达到退出条件不进入下一步。boot-arg 用 `songyuan_wlan=N`：`0` 关闭，`N` 做到第 N 步就停。不要复用 `fuxiwlan`，避免 0099 的地址表被带进来。固件放在内存里，不要写进根卷；这条根卷只剩几十 MB，Metal 已经因为空间不够拒绝过。

### M0 — 只读清单（不改内核）

在 Android 里补齐 §2 的固件目录，记下每个文件的大小和 sha256。同时从 `cnss2.ko` / `qca_cld3_peach_v2.ko` 里抽出：上电顺序、MHI 下载的文件名、QMI WLFW 的服务号、冷校准是一次掉电还是两次枚举。

MHI 镜像、BDF、regdb 已经在 §2 记下。`sbl_size` / `seg_len` 见 §5。这次启动日志没有请求 `phy_ucode`。内核里不放别的固件字节。

### M1 — 点亮 RC0，读到设备号

顺序以 cnss2 为准，不是 sheng 的 150 ms 低脉冲。`cnss_power_on_device()` 打开电源和 `rf_clk`，然后把 `wlan_en` 选到 active，再 `udelay(1000)`。PERST 不在这个函数里。随后 `cnss_resume_pci_link()` 交给 RC。上游 `pcie-qcom.c` 在 RC 初始化里先 assert PERST，PHY 和时钟起来之后按 PCIe CEM 的 TPVPERL 等 100 ms，再 deassert。GPIO16 和 `wl-reset-gpio` 是同一脚；active 状态在公开 peach pinctrl 里是 output-high。本机 `perst-gpio` 的 flags 是 0。PCIe CEM 里的 PERST# 信号本身是低有效，gpiod 的 assert 会不会把这脚拉高，取决于本机 PCIe 驱动用的是逻辑电平还是裸电平。第一次按本机驱动的写法做，不要先采用 sheng 的“脚为低就是复位”。

1. 七路 rail 按 `qcom,vdd-wlan-*-config` 投票，打开 `rf_clk`，WLAN_EN 进入 active，等待 1 ms。每路 rail 和 `rf_clk` 的开关状态挂在设备节点上，和 `cnss_power_on_device()` / `cnss_power_off_device()` 一样成对。不要只放在这次调用的局部变量里，否则 M3 冷校准无法按同一套状态回退。M1 本身不做冷校准。
2. RC：PCIe0 GDSC、PHY GDSC、`clock-names` 里的时钟、CLKREQ，再按驱动做 PERST 和 LTSSM。CRM 序列还没从本机驱动摘出，不要抄别的 SoC 的 CRM 常数。`qcom,phy-sequence` 若被本机 PCIe 驱动在 init 里消费，就属于这一步，不是失败后的补救。
3. 链路 down 时不要读端点配置空间。`PARF+0x1b0` 只打印，不参与判断。然后做一次出站 CFG 读。不要在循环里反复发配置周期。K90 在链路未起时读端点，USB 大约 8 秒后无应答。

日志必须出现：`vendor 17cb device 110e`，以及 BAR0 大小。读不到 `110e` 就停。出站 CFG 窗口是这次读设备号所必需的。入站窗不写。不下载固件，不碰窗口寄存器，不开 bus master。DBI 长度是 `0x10000000`，只映射头和要用的那一小段，不要整段映射。

地址只用 §1.2。RSC 用本机已经为触摸对过的 `rsc@18900000` drv@2，不要用 `fuxi_wlan.c` 里的 `0x17a20000`。

### M2 — BAR0 只读 dump，然后才下载

出站 MEM 窗口把 BAR0 放进 §1.2 第二组 `ranges`（`0x40300000`，长度 `0x3d00000`）。Android 这次把 BAR0 放在 `0x40400000`。不要用 0099 的 `0x60400000`，也不要把 DBI 基址当成 BAR。CPU 读 BAR0 不经过 SMMU。官方 `cnss_pci_enable_bus()` 在映射 BAR 时同时打开 memory space 和 bus master；PBL 阶段设备通常还不会主动 DMA。把 bus master 留到下载前，比 cnss2 更保守。只读 `MHIREGLEN`（0）、`MHIVER`（`0x8`）、`BHIOFF`（`0x28`）、`BHIEOFF`（`0x2c`）。非全 1 才算这块寄存器在。不要调用 `mhi_prepare_for_power_up()`，它在配了 RDDM 时会清 BHIE RX。

dump 通过之后才下载。镜像是 `peach/amss20.bin`。`sbl_size` 和 `seg_len` 都是 `0x80000`。SMMU 用 SID `0x1401`，BDF→SID 按 §1.4 写 PARF+`0x2054`。页表按 4 KiB granule 盖住 XNU 的 16 KiB 页，打开 bus master，缓存先清。门铃之后轮询 `BHI_STATUS` 到 2 或 3。停在 MHI 离开 RESET、还没发 WMI 之前。这一步仍然不写窗口寄存器。

退出条件：`BHI_STATUS` 的 `[31:30]` 为 2。若是 3 或 MHI SYSERR，先核对镜像是不是 `1107` 的 amss，以及 BDF→SID 有没有把端点写成 SID 0。

### M3 — QMI，冷校准，mission

按 `qca_cld3_peach_v2` 的顺序发 WLFW：IND register、能力、BDF、regdb、冷校准、mission。`qcom,wlan-cbc-enabled` 在设备树里，所以校准步骤留着。校准要求掉电再枚举时，M1 的上电函数要能重入，而不是在内核里死等。

退出条件：mission 的 QMI 应答成功，固件给出的固件版本字符串打印出来。此步仍然没有 `en0`。

### M4 — 数据面

CE ring、WMI、一个扫描、一个关联。缓冲所有权按 §4：DMA 完成前驱动持有自己的拷贝。中断可以后补；第一条扫描允许像 0099 / redwood 那样用线程轮询，避免和现有的 PCIe MSI 编程缠在一起。

退出条件：日志里有对端 AP 的 SSID，或主动扫描返回非空列表。先不要做吞吐优化。

### M5 — 接上 iOS

把 hackios 那三件套移进来，射频边界指到 M4。`songyuan_wlan` 走到这一步时才发布 `en0` 和假的 `IO80211Controller`。`songyuan_wlan=1` 只表示停在 M1，不会让设置里出现 Wi-Fi。

退出条件：设置里出现 Wi-Fi，能列出 M4 已经能扫到的那个 AP，关联后 `en0` 拿到地址。坐标、固件包大小、Metal 缓存那些和触摸/根卷有关的问题不要混进这次验收。

## 10. PARF 窗口/DBI/iATU 的硬件机制与正确编程（2026-11-06，上游驱动 + 本机 vendor 对照）

本节记录 M1 实测到"DBI 全 F、配置读全 F"之后的根因分析，以及据此修正的窗口编程。

### 10.1 硬件机制（Qualcomm 上游驱动说明）

- PARF 是 DWC 控制器外面的包装层；它**按 `PARF_SLV_ADDR_SPACE_SIZE`（默认 0x1000000 = 16 MiB）为步长，周期性镜像 DBI 与 ATU 寄存器空间**；
- **DBI/ATU 在系统内存中的位置由 `PARF_DBI_BASE_ADDR`、`PARF_ATU_BASE_ADDR` 决定**，硬件自己不知道 DT 里的地址；
- 若 DBI/ATU 落在镜像区间之外/与 BAR 区重叠，会出现"DBI 内容出现在非预期地址"甚至 NoC 访问 stall；
- **新 IP（2.7.0 及之后，x1e80100/sa8775p 等）的正确写法**：把 `PARF_SLV_ADDR_SPACE_SIZE` 与 `_HI` 都写 `0xFFFFFFFF`（U64_MAX，彻底关镜像），并显式写 DBI/ATU 物理基址。
  参考：https://lore.kernel.org/all/8877e1f7-bbb6-49e9-a30c-0ae8e40bf5dd@quicinc.com/T/#t

### 10.2 本机 vendor（同 SoC，`pci-msm` 反汇编）的 PARF 编程顺序

`msm_pcie_enable_link.c`（本机驱动，行号见文件）：
```
parf+0x1000 = 4      DEVICE_TYPE=RC
parf+0x40  &= ~1     PHY_CTRL
parf+0x00   = 0x365E SYS_CTRL
parf+0x174 |= 0x10   MHI clock reset bypass
parf+0x22C = 0 → 0x7F80D202  INT_ALL_MASK
parf+0x350/0x354 = DBI 物理基址
parf+0x634/0x638 = ATU 物理基址
parf+0x358 = 0, parf+0x35C = 0x80000000   ← 老式"关镜像"值
parf+0x1A8 |= 0x80000000  AXI_MSTR halt
parf+0x4A0 / 0x50C 等
→ PHY 序列(199 写) → pipe clock → 等 ep_latency(10 ms) → PERST 释放
→ 等 perst_delay_us(1 ms) → dm_core 0x80C/0x8A8/0x8AC/0x8BC(GEN3 配置)
→ 最后 parf+0x1B0 |= 0x100 (LTSSM_EN)
```
注意：vendor **在 PHY 初始化之前不会读 DBI**；DBI 的第一次使用是在 PHY/链路相关配置阶段。

### 10.3 我们的错误与修正

- 最初照 K90 写了 `0x358=0/0x35C=0x80000000`（老式值），并且**写完立刻读 DBI** → DBI 访问 stall（ticket spinlock 超时复位）；
- 之后直接删掉这两条 → PARF 保留引导程序默认值（实测 `slv_lo=0x1000000, slv_hi=0`）→ DBI 被按 16 MiB 步长镜像，`0x400000000` 处读回 `0xffffffff`；iATU 的窗口也受同一镜像规则影响，配置读全 F 不能直接归因于"链路没起来"；
- **修正（照上游新 IP 写法）**：
  ```
  0x350/0x354 = DBI 物理基址 (本机 0x400000000 → 0, 4)
  0x634/0x638 = ATU 物理基址 (本机 0x410000000 → 0x10000000, 4)
  0x358 = 0xFFFFFFFF, 0x35C = 0xFFFFFFFF
  ```
  并把 DBI 的读取移到 **PHY 初始化之后**（与 vendor 一致），先确认 DBI 是否变成 `0x17cb0123`；若 DBI 正常而配置读仍全 F，再集中查链路训练（PHY/PERST/refclk/dm_core GEN3 配置）。

### 10.4 教训（写进规则）

1. 窗口/镜像这类寄存器必须按**本机 IP 代际**的驱动（上游 pcie-qcom 最新分支 / vendor 反汇编）核对，不能只抄老 SoC 或 K90；
2. 写窗口寄存器后**不要在未完成 PHY/链路初始化时立即访问 DBI**（会导致 NoC stall 与看门狗复位）；
3. M1 的通过条件仍然只有配置空间 `17cb:110e`；DBI/窗口读数只作调试日志。

## 11. M1 实测进展（2026-11-06）：RC 侧已通则，根因在端点侧

### 11.1 已确认修复：PARF 窗口（§10 落地结果，kernel_17+）

### 12.0 标准 PCI 使能流程（2026-11-06 补充，必做）

> 教训：BAR 地址/窗口都对了，但设备没被"使能"（D0 + Command），第一次 BAR0 读就 completion timeout → 内核挂死。
> Linux PCI 核心替 vendor 做了下面 3、4 步，裸写寄存器必须自己补。

```
1. 读 BAR 并 sizing（§12.1）
2. 写 BAR 地址（BAR0/BAR2）
3. 电源状态回到 D0：遍历 config 能力链找 PM capability(ID 0x01)，
   读 PMCSR(cap+4)，若 state!=D0 则写 0 并回读确认
4. Command 寄存器 = Memory Space Enable | Bus Master Enable（0x6），回读确认
5. 以上都确认后，才允许访问 BAR（MHI/BHI 读取）
```

实现要点（本机已落地）：
- 32 位 config 读必须 4 字节对齐；16 位字段（PMCSR/Command）用「对齐 32 位读 + 移位」或 16 位写；
- 打印 `PCI enable: pm cap … pmcsr … -> …; cmd … -> …` 作为验收证据；
- 未确认 D0/Command 时**跳过 BAR 读**，不允许再出现 completion timeout 挂死。

### 13.4 方案锁定规则（M2 起强制，违反即视为缺陷）

1. **出站 MEM 窗口**：必须用 DT `ranges` 第二组整段、恒等映射（本机 `0x40300000`，长度 `0x3d00000`），不允许只从 BAR0 起、不允许用 0099 的 `0x60400000`；
2. **Command 寄存器**：M2 阶段只置 `MEMORY`（`0x2`）；**bus master（`0x4`）留到 MHI 阶段**；
3. **BAR0 读取**：只映射实际读取的 4 KiB 页面、先读 1 个 32 位字；禁止整段 2 MiB 映射；
4. **判据**：不读 BAR0 就当 M1 完成；BAR0 读必须在 D0 + MEMORY 确认之后；
5. **fault 处理**：读失败必须记录并跳过，不允许裸读导致 panic；需要容错时按 fuxi `fuxi_gpu_access` 方案；
6. **执行纪律**：任何"临时绕过方案"的写法都必须先在本文档改方案、再改代码；`prebuild_checks.py` 第 7 组检查会拦住违反 1-3 的提交。
7. **SMMU 槽/CB 禁止写死**：SMMU 的 stream slot、context bank、页表、DMA 池必须在运行时先只读探测、再当场编程（写前打印旧值、写后回读、TLBI 之后才允许 BHI）；不得把别的机型（fuxi/K90）的槽号、CB 号、IOVA 常量直接写死。

> 教训：kernel_31..kernel_36 的 BAR0 崩溃全部来自 M2 实现偏离本节（窗口只覆盖 BAR0 附近、提前开 bus master、2 MiB 大映射、无 fault 处理）。

### 13.8 SMMU bring-up 分两级（2026-11-08 起）

kernel_45 证明：**直接写 CB（context bank）寄存器会挂死**（CB 页在 0x15080000 处，写即 panic/重启；读正常）。因此 SMMU 分两级：

1. **14a（先做）**：`S2CR[slot] = 1<<16`（bypass，type 1）+ `SMR[slot]=0x80001401`，只写 GR0 窗口（已映射），**不碰 CB 页**；DMA 使用**物理地址**，BHI SBL 的镜像缓冲必须 `kmem_alloc_contig` 连续且 <4 GiB；
2. **14b（后做）**：确认 bypass 路径可 DMA 后，再按 fuxi 顺序写 CB（SCTLR/CBAR/CBA2R/TCR/TTBR/MAIR/TLBI），并切到 S1 翻译 + IOVA `0xB0000000` 身份页表。

规则：**在 bypass 跑通（BHI SBL code=2）之前，禁止写任何 CB 寄存器**；CB 写操作必须单独成阶段并带 `GR1/CB map failed` 守卫。
