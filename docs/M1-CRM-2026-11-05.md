# M1 / PCIe RC0：CRM D0 实现与实测（2026-11-05）

## 1. 为什么按文档做 M1 还会失败

文档 §6 M1-2 明确写了"CRM 序列还没从本机驱动摘出，不要抄别的 SoC 的 CRM 常数"——**文档的 M1 步骤清单里本来就缺 CRM（CESTA D0）这一步**。
本机 DT 是 `qcom,drv-name="cesta"` + `pcie_sm` 节点（CESTA 模式）；官方 `msm_pcie_enable()` 的顺序是：

```
PERST → rails → GDSC → clk_init（含 ICC/CRM 投票）
→ msm_pcie_enable_cesta()：map_save(bw_gen_max) + map_apply(D0)   ← 文档没列
→ core/phy reset → PARF → PHY/pipe → LTSSM → 配置读
```

`enable_cesta()` 失败会直接中止 enable。所以"按文档"把能列出的步骤都做成功（power_on/BCR/时钟/PHY/PERST/LTSSM_EN），核心仍然不上电 → 配置读全 F。

## 2. 本机官方源码（已获取并对照）

- 仓库：`OnePlusOSS/android_kernel_oneplus_sm8850`，分支 `oneplus/sm8850_b_16.0_oneplus_15t`（OnePlus 13T）；
- 文件：`drivers/soc/qcom/crm-v2.c`（69,739 B）、`include/soc/qcom/crm.h`（3,845 B）；
- 与 live.dtb 逐项对上：`/soc/crm@1d01000`，compatible `qcom,pcie-crm-v3`，reg 次序 base/crm_b/crm_b_pt/crm_c/crm_v/common（0x1d01000/0x1d03000/0x1d03400/0x1d03800/0x1d05800/0x1d05e00）、`hw-drv-ids=[0,1]`、`sw-drv-ids=[0]`；
- 关键 API：`crm_write_perf_ol()`（HW 只缓存投票）、`crm_write_pwr_states()`（flush 缓存 + 切通道）、`crm_cache_vcd_votes()`；
- `pcie_crm_desc_v3` 的偏移：`CHN_BUSY=0x370`、`CHN_UPDATE=0x374`、PERF_OL `PWR_ST0..4=0x0/4/8/c/10`、`PWR_ST_CHN_DISTANCE=0x14`、`DRV_RESOURCE_DISTANCE=0x2c`、`DRV_DISTANCE=0x1000`、BW_PT `PWR_ST0_PT..=0xb0..0xc0`；
- 配置计数从 common 块读：`num_pwr_states=cfg[3:0]`、`num_channels=cfg[5:4]`、`num_perf_ol_vcds=cfg[9:6]`、`num_nds_pt=cfg[30:26]`；
- 本机 Android 侧 CRM IPC 日志（debugfs `ipc_logging/pcie_crm_hw_drv_0`）实测：pwr_state 0–4（5 个）、PERF_OL resource 0–1（2 个）、BW_PT resource 0–15（16 个）、`Switch Channel: ch:0 ret:0`。

## 3. 已实现（`songyuan_wlan.c`，补丁 0350）

- 映射 CRM `base` 0x1d01000（0x2000）；
- `sy_crm_d0()`：
  1. 读 `0x374` 选空闲通道（0→ch0，bit0→ch1，bit1→ch0）；
  2. PERF_OL：res0/pwr0,pwr1 写 4（`bw_gen_max(3)+PERF_LVL_L1SS(1)`），其余 0；
  3. BW_PT：16×5 全 0；
  4. 写 `0x374 = 1<<ch` 触发；轮询 `0x370 & (1<<ch)`，100×100 µs；
- 调用点：clocks 之后、core/phy reset 之前（与 vendor 顺序一致）。

### 6.1 结论：DBI 一直不可读，且找到了两个我们自己的问题

1. **DBI 在 PHY 之后仍是 `0xffffffff`** —— 说明"读早了"不是唯一原因；核心/PARF 的 DBI 路径确实没通。
2. **我们自己的 link-active 判断有 bug**：`dbi80=0xffffffff` 的 bit29 被当成 LINK_ACTIVE，所以"等待链路"0 ms 就退出了（这行 `link active after 0 ms` 是误报），实际上根本没等。
3. **PARF `SLV_ADDR_SPACE_SIZE` 没有被程序**：现场是 `slv_lo=0x1000000, slv_hi=0`；官方/K90 可用实现写的是 `0x358=0, 0x35c=0x80000000`。这一项正是 PARF 对 DBI/ATU 窗口的地址译码配置，未写入时 DBI 访问被错误路由/拒绝，`0xffffffff` 与此吻合。
4. `atu_lo=0x10000000, atu_hi=0x4`（= `0x410000000`，与 DT 一致）、`dev-type=0x4`、`sys=0x365e` 均正确。
5. `aux/rchng/pipe` 的 CBCR 读回都是 `0x08000000`（bit27），不是 CLK_OFF(bit31)；但 **rchng RCG 从未配置过**（canoe: `gcc_pcie_0_phy_rchng_clk_src` cmd_rcgr=`0x6b078`），下一轮需要补。
6. `int_mask=0x7fc0bb2e` 仍是引导程序值；`int2=0x6000410`。对 M1 的 config read 非必需，但 K90/vendor 会先清零再按位使能。
7. `PARF_LTSSM` 始终 `0x100`（bit8=EN，state=0）；文档 §6 已提示 canoe 的 LTSSM 布局可能不同（sm8550 才是 [5:0]/bit8），所以这一读数**不能单独作为链路判断依据**。

### 6.2 第二轮改动清单（按依赖顺序）

1. `sy_parf_setup()` 里按 vendor/K90 顺序补：`0x358=0`、`0x35c=0x80000000`（在 DBI/ATU base 之后）；再写 `0x22c/0x50c` 的清零+按位使能（可选）。
2. 修 link-active 判断：`(dbi80 != 0xffffffffu) && (dbi80 & (1u<<29))`，并同时要求 `dbi0 != 0xffffffff`。
3. 补 **root port 头**（DBI 可读之后、PERST 释放之前，按 K90 `root_port_setup`）：BAR0 64-bit、bus primary/secondary/subordinate=0/1/0xff、COMMAND、class `0x0604`、Link speed Gen1。
4. 补 rchng RCG：`0x6b078`，配置值按 gcc-canoe 的 `ftbl_gcc_pcie_0_phy_rchng_clk_src`（下一轮先读当前 RCG 配置再定）。
5. `LTSSM` 改用 DT 的 `qcom,pcie-sm-debug` 偏移（14 个 u32）读状态，或在 DBI 可读后用 `DBI 0x80 LINK_ACTIVE` 判定；PARF 0x1b0 只做旁证。
6. 只有上述都就绪、且链路状态指示 up 之后，才做那一次出站 config read。
